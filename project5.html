Vibecoding a Weekend Bucket List App

Designing and building a full-stack web app from scratch over a weekend using AI-assisted development — an experiment in speed, taste, and what it means to be a designer who codes.

Role Designer & Developer
Timeline 1 weekend
Focus Personal project
Stack React · Node · AI tooling

Overview

I've always had a long list of things I want to do in San Francisco — hikes, hidden bars, neighbourhood restaurants, weekend trips. Most of them live in a Notes app, half-finished and never revisited. I decided to actually build the thing I wished existed: a personal bucket list app designed around how I actually plan my weekends.

The project was as much an experiment in process as in product. I used Cursor and Claude to accelerate development, handling the parts I'd normally spend the most time on — component wiring, API integration, deployment config — so I could focus on the design decisions that actually matter.

App overview screenshot

The finished app — a personal bucket list tool built over a single weekend

The idea

The concept was simple: a lightweight app where I could log things I wanted to do, tag them by category and effort level, and surface them when I had a free Saturday afternoon. No social features, no gamification — just a clean, personal planning tool.

I started with a quick sketch of the core flow: add an item, view the list filtered by type, mark it done. I wanted the UI to feel considered and editorial — not another generic to-do app — so I spent time early on establishing the visual language before writing a line of code.

Speed over perfection

The constraint was the point. One weekend forced ruthless prioritisation — only the features that would actually change how I use the app made the cut.

Design first, build second

Even with AI assistance speeding up development, the design decisions still required human judgement. I spent the first morning on layout and visual language before touching code.

Ship something real

The goal was a deployed, usable app — not a prototype. That accountability shaped every tradeoff, from scope to tech stack to error states.

The process

I used Cursor as my IDE and leaned heavily on Claude for scaffolding boilerplate, debugging weird edge cases, and generating the more repetitive parts of the codebase. What surprised me was how much design thinking it required to direct the AI well — vague prompts produced vague output. The clearer my design intent, the better the code.

The experience crystallised something I'd suspected: AI-assisted development doesn't remove the need for design skill, it concentrates it. You spend less time on syntax and more time on decisions — which is a better use of a designer's time anyway.

Process screenshot — Cursor + Claude in action

Using AI tooling to handle the scaffolding, while staying close to the design decisions that mattered

The clearest signal that the experiment worked: I still use the app every weekend. It's earned a permanent place on my home screen, which is more than I can say for most side projects.

What I learned

Building something end-to-end — even something small — is a fundamentally different experience from handing off designs to an engineering team. You feel every friction point in the UX viscerally, because you're also the person debugging it at 11pm on a Saturday.

AI-assisted development significantly lowered the barrier to shipping. But it didn't lower the bar for quality — if anything, it raised it, because there were no longer any good excuses for skipping the hard design thinking. The time saved on boilerplate went straight into sweating the details.

I came away from the weekend more confident in my ability to move between design and code fluidly — and more convinced that designers who can build are going to be increasingly valuable as AI continues to compress development timelines.
